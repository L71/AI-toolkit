# llm_service.py

A small Python utility for managing Ollama and llama-server as persistent macOS
background services — independently of Homebrew.

---

## Background: why does this exist?

When you install Ollama or llama.cpp via Homebrew and start them with
`brew services start`, Homebrew generates a launchd property list (plist) file
and registers it with macOS's service manager. This works, but has a frustrating
limitation: there is no official way to inject your own environment variables
into a Homebrew-managed service. The plist is owned and regenerated by Homebrew,
so any manual edits get silently overwritten on the next `brew upgrade` or
`brew services restart`.

### A brief primer on launchd and plists

macOS uses a subsystem called **launchd** to manage background services (similar
to `systemd` on Linux). Each service is described by a **plist** — an XML file
that tells launchd what binary to run, what environment variables to pass it,
whether to restart it on crash, and so on.

Plist files for user services live in `~/Library/LaunchAgents/`. Homebrew writes
its own plists there, and considers them its own property — it can regenerate or
delete them at any time.

The clean solution is to create **separate plists** with different service labels
that Homebrew is completely unaware of. That is exactly what `llm_service.py`
does — one independent service for Ollama, one for llama-server, each managed
entirely via its own plist and env file.

---

## What the script does

- Reads environment variables from a simple `KEY=VALUE` text file.
- Generates a valid launchd plist for the chosen service.
- Registers and manages that service via `launchctl` — the command-line
  interface to launchd.
- Leaves Homebrew's plists completely untouched.

Both services use labels that Homebrew will never touch:

| Service | Plist label | Plist file |
|---|---|---|
| Ollama | `local.ollama.serve` | `~/Library/LaunchAgents/local.ollama.serve.plist` |
| llama-server | `local.llama-server.serve` | `~/Library/LaunchAgents/local.llama-server.serve.plist` |

---

## Requirements

- macOS (any reasonably recent version)
- Python 3.9 or later (ships with macOS, or via Homebrew)
- Ollama and/or llama.cpp installed via Homebrew:
  ```bash
  brew install ollama        # for the Ollama service
  brew install llama.cpp     # for the llama-server service
  ```

No third-party Python packages are required.

---

## Command syntax

```
python3 llm_service.py <service> <command> [env_file]
```

**Services:** `ollama` or `llama`

**Commands:**

| Command | What it does |
|---|---|
| `install [env_file]` | Write plist from env file, then load the service |
| `load` | Start the service (plist must already exist) |
| `unload` | Stop the service |
| `reload` | Stop then start (useful after editing the env file) |
| `status` | Show whether the service is running, its PID, and log path |
| `uninstall` | Stop the service and delete the plist |

## Quick start: Ollama

### 1. Stop the Homebrew-managed Ollama service (if running)

```bash
brew services stop ollama
```

### 2. Create your environment file

```bash
mkdir -p ~/.ollama
nano ~/.ollama/env
```

Add your desired settings, one per line:

```
# Listen on all network interfaces (not just localhost)
OLLAMA_HOST=0.0.0.0

# Allow cross-origin requests (useful for local web UIs)
OLLAMA_ORIGINS=*

# Unload models from GPU after 10 minutes of inactivity
OLLAMA_KEEP_ALIVE=10m
```

Lines starting with `#` and blank lines are ignored.

### 3. Install and start the service

```bash
python3 llm_service.py ollama install
```

This writes the plist, registers it with launchd, and starts Ollama immediately.
The service will also auto-start at every login.

### 4. Verify it is running

```bash
python3 llm_service.py ollama status
```

You should see something like:

```
Service: local.ollama.serve
Plist:   /Users/you/Library/LaunchAgents/local.ollama.serve.plist
Status:  running  (PID 12345)
Log:     /Users/you/.ollama/ollama.log
```

Confirm Ollama is reachable:

```bash
curl http://localhost:11434
# → Ollama is running
```

## Quick start: llama-server

llama-server is the HTTP server that ships with llama.cpp. When started in
**router mode** (no model specified at startup), it dynamically loads and
unloads models on demand — similar to Ollama's behaviour — using models from
a directory you specify.

### 1. Stop the Homebrew-managed llama.cpp service (if running)

```bash
brew services stop llama.cpp
```

### 2. Create your environment file

The script will create the config directory automatically on first run, but you
can do it manually:

```bash
mkdir -p ~/.config/llama-server
nano ~/.config/llama-server/env
```

A typical router-mode setup:

```
# Listen on all interfaces
LLAMA_ARG_HOST=0.0.0.0

# Port (default is 8080)
LLAMA_ARG_PORT=8080

# Directory of GGUF model files for router mode
LLAMA_ARG_MODELS_DIR=/Users/you/models

# GPU layers — set to 99 to offload everything to Metal
LLAMA_ARG_N_GPU_LAYERS=99

# Default context size for all models
LLAMA_ARG_CTX_SIZE=8192

# Unload model from GPU after 5 minutes of inactivity
LLAMA_ARG_SLEEP_IDLE_SECONDS=300
```

### 3. Install and start the service

```bash
python3 llm_service.py llama install
```

### 4. Verify it is running

```bash
python3 llm_service.py llama status
```

Confirm llama-server is reachable and list available models:

```bash
curl http://localhost:8080/v1/models
```

---

## Updating your configuration

Edit the relevant env file, then re-run `install` — it handles the stop/start
cycle automatically. There is no need to manually unload first.

```bash
# Ollama
nano ~/.ollama/env
python3 llm_service.py ollama install

# llama-server
nano ~/.config/llama-server/env
python3 llm_service.py llama install
```

## Common environment variables

### Ollama

| Variable | Example | Effect |
|---|---|---|
| `OLLAMA_HOST` | `0.0.0.0` | Listen on all interfaces, not just localhost |
| `OLLAMA_ORIGINS` | `*` | Allow cross-origin requests (needed by some UIs) |
| `OLLAMA_KEEP_ALIVE` | `10m`, `1h`, `-1` | How long to keep a model in GPU memory; `-1` = forever |
| `OLLAMA_MODELS` | `/Volumes/Data/ollama/models` | Store models on a different disk |
| `OLLAMA_CONTEXT_LENGTH` | `8192` | Default context window size |
| `OLLAMA_DEBUG` | `1` | Enable verbose debug logging |

### llama-server

llama-server environment variables use the `LLAMA_ARG_` prefix, which maps
directly to command-line arguments (e.g. `LLAMA_ARG_CTX_SIZE` = `--ctx-size`).

| Variable | Example | Effect |
|---|---|---|
| `LLAMA_ARG_HOST` | `0.0.0.0` | Listen on all interfaces |
| `LLAMA_ARG_PORT` | `8080` | Port to listen on |
| `LLAMA_ARG_MODELS_DIR` | `/Users/you/models` | Directory of GGUF files for router mode |
| `LLAMA_ARG_N_GPU_LAYERS` | `99` | Layers to offload to Metal GPU; 99 = all |
| `LLAMA_ARG_CTX_SIZE` | `8192` | Context window size |
| `LLAMA_ARG_SLEEP_IDLE_SECONDS` | `300` | Unload model from GPU after N seconds idle |
| `LLAMA_ARG_MODELS_MAX` | `2` | Maximum models loaded simultaneously (router mode) |
| `LLAMA_ARG_FLASH_ATTN` | `1` | Enable flash attention (faster, less memory) |
| `LLAMA_LOG_LEVEL` | `info` | Log verbosity (`debug`, `info`, `warn`, `error`) |

## Running Ollama and llama-server side by side

Both services can be installed and managed independently. They use different
ports (11434 and 8080 by default) and different GPU memory allocations, so they
do not directly conflict at the system level.

However, on Apple Silicon both use the Metal backend and draw from the same
unified memory pool. If both have models loaded simultaneously, they will compete
for GPU memory, which can degrade performance or cause one to spill layers to CPU.

The cleanest way to share a Mac between both services is to configure idle
unloading so each releases GPU memory when not in use:

```
# ~/.ollama/env
OLLAMA_KEEP_ALIVE=1m

# ~/.config/llama-server/env
LLAMA_ARG_SLEEP_IDLE_SECONDS=60
```

With these settings, whichever service finishes a request first will release the
GPU within a minute, leaving it available for the other.

## Coexisting with Homebrew

The script's service labels (`local.ollama.serve`, `local.llama-server.serve`)
are completely unknown to Homebrew, so `brew upgrade`, `brew services restart`,
and similar commands will never touch them.

The only rule is: don't run both the Homebrew-managed and the script-managed
version of the same server simultaneously, as they would compete for the same
port. Stop the Homebrew version once, and use this script exclusively going
forward.

To revert either service back to Homebrew management:

```bash
python3 llm_service.py ollama uninstall
brew services start ollama

python3 llm_service.py llama uninstall
brew services start llama.cpp
```

## Troubleshooting

**Service shows as stopped with a non-zero exit code**

Check the log for errors:
```bash
tail -50 ~/.ollama/ollama.log
tail -50 ~/.config/llama-server/llama-server.log
```
Common causes: a typo in a variable name, a port already in use, or the binary
not found at the expected path.

**Binary not found warning during install**

The script looks for binaries at the standard Homebrew locations for Apple
Silicon (`/opt/homebrew/bin/`) and Intel (`/usr/local/bin/`). If your setup
differs, edit the `bin_candidates` list for the relevant service in the
`SERVICES` dict near the top of the script.

**Inspecting the generated plist**

```bash
cat ~/Library/LaunchAgents/local.ollama.serve.plist
cat ~/Library/LaunchAgents/local.llama-server.serve.plist
```

**llama-server in router mode doesn't see a newly added model**

Router mode scans the models directory at startup only — it does not watch for
new files. After adding a GGUF file to your models directory, reload the service:
```bash
python3 llm_service.py llama reload
```
Alternatively, download models through llama-server's own `-hf` mechanism, which
makes them available without a restart.

**Reverting both services to Homebrew**

```bash
python3 llm_service.py ollama uninstall
python3 llm_service.py llama  uninstall
brew services start ollama
brew services start llama.cpp
```
